# Tabletop Map architecture

## Ownership and state

`server.js` hosts the DM and table routes and owns one saved workspace, with multiple campaigns and their sessions. DM JSON mutations are serialized, guarded by expected revision, validated by `model.js`, and committed through `store.js` before publication. Local DM routes trust the local computer. The server rejects writes with unrelated browser origins and restricts Host to loopback or a detected local IPv4 interface address. The optional character extension adds a narrowly restricted LAN controller surface, described below.

Saved schema version 2 stores a campaign workspace, separate DM selection and published map, persistent emergency blank state and monotonic revision. Version-1 saves migrate into one campaign/session with their original progress. Each map holds an immutable asset, dimensions, visibility operations and history cursor, grid calibration, and locked table geometry. DM navigation is browser-local transient state. Actual player viewport size is recorded separately without altering map geometry. Images are identified by generated IDs; imported files never overwrite existing maps.

The fog journal supports brush, rectangle, polygon, and whole-map operations. Reveal removes fog; cover restores opaque fog. The journal starts covered, supports disconnected areas, and saves both undo and redo history. Composition is shared between player and preview. This is manual discovery, not character-dependent visibility.

## Fail-closed rendering and transport

The table HTML begins with black CSS and a black canvas. A snapshot clears the visible canvas, loads its asset asynchronously, renders grid/map/fog entirely offscreen, and publishes only the completed composition. A generation counter rejects late asset loads from older snapshots, and older revisions are ignored. Blank snapshots never publish map pixels. The table does not draw the unmasked source onto its visible canvas at any point.

Server-sent events provide prompt updates and one-second pulses. A one-second authoritative snapshot poll is a fallback for browser streams stalled after an offline transition. Failed requests clear the display; missing pulses/successful polls blank it after three seconds (checked every half second). Reconnect fetches the current snapshot rather than reusing an old visible frame. This watchdog blanking is bounded, not instantaneous cable-failure detection. Normal rendering still requires a responsive browser process.

The DM learns whether a table browser is present through one-second heartbeats, expiring after 3.5 seconds. The embedded preview never sends table heartbeats. Presence is distinct from proof that pixels are physically visible: a minimized window, OS display change, or disabled monitor can still have a live browser heartbeat.

Table input never pans or zooms the map. Deliberate geometry/grid changes, including rotation, are available only in the DM view and are also rejected by the server while locked. Rotation applies to the completed fogged composition about its center; X/Y anchor its rotated bounding box. Fit uses those bounds, and rotation leaves source-map coordinates and physical scale unchanged. Older schema-1 saves without a rotation field load as 0°. OS/browser display changes remain outside that lock.

## Persistence

Save writes a temporary session file, flushes it, copies the prior session to `.bak`, and renames the temporary file over the live file. In-memory saved state advances only after save succeeds. Emergency blank is the deliberate exception: a fail-closed transport override publishes immediately, ahead of pending disk writes, then persists in the serialized queue. A newer blank cannot be cleared by an older pending Show command. If saving the blank fails, the transport stays blank until a successful explicit Show. This protects against failed writes and partial JSON replacement; it is not a guarantee against disk failure, sync-provider interference, or every possible power-loss scenario. Corrupt or unsupported saved schemas stop startup. Session export includes asset bytes and state in one consistent snapshot. Restore creates a new directory and never overwrites existing data.

## Extension boundaries

Server-owned session state, transport snapshots, asset storage, and the shared composition renderer are separate modules. Walls/doors/light sources can later use the same source-map coordinates. A future lighting engine can replace or combine with the manual fog journal and circle visibility. Character sheets, rules enforcement, collision detection, and campaign tools remain outside scope.

## Optional character extension

`characters.js` defines per-map tokens and separate retained exploration circles. Schema-1 saves migrate to disabled character mode and Wi-Fi disabled, preserving the original composition. Tokens store name, color, source-map position, reveal radius in grid squares, generated ID, and 192-bit random controller key. Normal table snapshots omit every controller key. A deliberate DM QR invitation temporarily includes one encoded private controller link in the local table snapshot, as described below. DM-only session backups include those keys for restoration.

Rendering starts with opaque fog, optionally removes retained character exploration, applies manual reveal/cover operations, and finally removes current character circles. This makes manual cover authoritative over retained trails, while the union of current character circles always stays visible. Tokens are drawn only on the final composition after fog. Switching visibility mode retains exploration memory but changes whether it is rendered; disabling characters returns to the manual-only map. Original map coordinates, table calibration and lock are unchanged.

Player movement is a discrete server command identified by a bearer key and expected map ID. It moves only the assigned token on the currently active map, inverse-rotates the displayed direction to the nearest source-grid direction, remembers exploration if enabled, and persists before broadcasting. All token placement uses complete grid-square centers and rejects occupied destinations, including hidden encounters. New tokens find the nearest free square; saved sessions and grid recalibration align existing tokens in stable order and separate overlaps. If no complete/free square exists, the operation fails. Token strokes scale with the grid to remain inside the square even with very small calibration values. Movement is serialized without a global expected revision so concurrent players cannot occupy the same square or overwrite one another. DM commands retry revision conflicts up to twice only if the active map is unchanged.

The server listens on IPv4 interfaces, but remote clients are rejected by default. When the saved Wi-Fi setting is enabled, non-loopback connections may access only the controller HTML/JS/CSS and the key-protected own-character state/movement endpoints. DM HTML/APIs, map assets, table snapshots/events, backups, and table display remain loopback-only. Controller links put keys in URL fragments, then send them as Authorization headers; source map bytes never reach the phone controller. Shared-table rendering still occurs on the trusted DM computer.

This access model is for a trusted home/local gaming network over HTTP, not internet hosting. Windows firewall allowance and network client isolation affect physical phone connectivity. A connected phone is not a table heartbeat. Multi-client movement and restriction tests cover an actual local interface address, but real phones/tablets and the group's Wi-Fi remain separate human acceptance.

## Adventure tools — October 5, 2026

Tokens retain their stable IDs and add a default `player` kind, visible flag and optional inline PNG artwork. Old tokens migrate as visible players. New monsters/NPCs default hidden and must have zero radius. Controller lookup and movement reject non-player tokens; encounter keys stay DM-only even though they have no supported controller. Public token snapshots exclude hidden tokens entirely. Encounter tokens draw before fog, including when character mode is off; player tokens draw after fog when enabled. Hidden encounters draw only in the DM overlay. Artwork uploads are center-cropped client-side to 256 × 256 PNG, bounded during validation, cached for rendering, and included directly in saved session/backup data.

`/api/roll` accepts a dice expression and mode, generates results with the bundled Web Crypto dice engine, and returns the exact published result. LAN requests require an assigned active, visible player bearer key; attribution comes from that token rather than request data. Local DM rolls use DM attribution. Origin/Host checks and the existing Wi-Fi gate still apply. A per-owner one-second limit bounds repeated sharing. The last three shared cards have a 12-second expiry and an ephemeral sequence separate from saved revisions; SSE and polling synchronize them without disk writes or changes to fog/token state. PostMessage bridges check origin and the exact embedded frame, and only pass expression/mode and results. Correlation IDs work on local-network HTTP without requiring a secure-context UUID API. Uncertain requests are not automatically repeated.

Per-map atmosphere defaults to no effect/no sound and validates a fixed preset list and volume. A bounded-resolution visibility mask mirrors the fog/exploration composition, transforms with table geometry, and clips a transparent screen overlay. Effects have no input handling or geometry mutation. Moving rain/embers stop under reduced motion; mist becomes static. Web Audio noise/filter presets start only following a table gesture, stay silent in previews, and stop when the table is blank or its connection watchdog fails. Table refresh requires a new audio gesture. Audio and effect appearance/performance on real hardware remain human acceptance.


## QR invitations — October 7, 2026

The loopback-only POST `/api/invite` endpoint accepts an active map/player ID and an address from the server's detected IPv4 interfaces, or a clear command. It checks Wi-Fi, enabled character mode, visible player kind and map identity before generating a QR SVG with bundled qrcode-generator 1.4.4. Requests cannot supply an arbitrary URL or key. The local table snapshot includes an ephemeral invite card with the SVG, character name and two-minute expiry, plus an independent sequence for SSE/poll synchronization. It contains an encoded private link only during this explicit DM sharing operation; LAN clients still cannot fetch table snapshots, invites, assets or DM APIs. Ordinary player token snapshots continue to omit keys.

Invitations never enter session saves or backups and start empty after restart. Removal, hiding, disabling minis/Wi-Fi, switching maps and expiry discard the card permanently; emergency blank clears it immediately before persistence. A new QR can be deliberately shown over a blank map for onboarding. The table overlay preserves the underlying canvas composition and geometry, uses a four-module white quiet zone, and clears on disconnect through the existing watchdog. Hiding/expiry affects the card, not the lifetime of the original character credential.


## Player character customization — October 7, 2026

POST `/api/character` is the additional Wi-Fi allowlisted profile endpoint. It requires the player's existing bearer key and its assigned map ID. `customizeCharacter` resolves only that key's player token, accepts only name/artwork fields, validates them, clones the latest session and advances its revision. It permits preparation while the map/minis are inactive. No positions, fog, exploration, controller identity or DM settings change. Saving uses the same serialized persistence queue and publishes only after a successful write, preserving concurrent movement. Removed characters and encounter credentials cannot customize a profile. Normal Origin/Host and Wi-Fi restrictions apply.

The controller provides an explicit Save/Cancel form with a client-side 256-square PNG crop and avatar removal. Its dirty draft survives background polling and failed saves; older response revisions cannot overwrite a newer successful response. Arrow keys in text inputs do not move the mini. Name changes preserve the stable ID, private URL and dice scope. Profile artwork uses the established validated inline PNG field and existing table renderer/backups.

## Optional native Windows display

`display-manager.js` supervises the optional Electron child in `desktop/`. Browser operation has no Electron dependency. GET /api/display reports capability without launching/downloading anything; POST accepts only discover/open/close, after existing loopback, Host and Origin checks. LAN controllers cannot access this endpoint. A short-lived loopback TCP channel authenticated by a random per-launch 256-bit token carries bounded command/reply messages; the token is never sent to the web UI or campaign backup. Closing the helper or server closes that channel.

The helper opens the same /table page with a desktop query flag in a frameless, fixed, always-on-top rectangle formed by two selected non-primary displays. Geometry rejects duplicates, missing screens, mismatched scaling and nonadjacent/nonrectangular layouts. It uses full display bounds in Electron DIP coordinates and does not alter Windows display configuration or rotate a screen a second time. Disconnect/layout changes close the window. Renderer Node access, preload bridges, permissions, popups, downloads, external requests and navigation are disabled. The fixed internal inspect/capture commands are available only on the authenticated supervisor channel for acceptance evidence; the HTTP API does not expose them or arbitrary evaluation.

Native heartbeat dimensions take priority only while its window is open. The transient snapshot displayMode flag suspends atmosphere in browser player windows while native display is active, avoiding duplicate sound; closing restores the previously enabled browser audio. The renderer still handles fog, blanking, streams, QR expiry and offline watchdog behavior. Display mode and monitor choices are browser-local preferences; the campaign schema is unchanged.


## DM modes — October 19, 2026

`app.js` owns browser-local `dmMode` and changes visibility on the existing DOM controls. Setup and Game-Play share the same canvas, token selection, action queue, preview frame and server state. Mode switching never calls an API, reloads frames, saves a mode into campaign data, changes the active map, or resets DM navigation. Canvas tool choices and sidebar scroll positions are retained separately for each mode. The emergency header controls stay shared.

Unapplied form values are retained in an in-memory map keyed by active map, token identity where relevant, and field ID. Polling renders authoritative state and then restores that page's drafts. Successful actions clear only submitted fields whose drafts have not changed while waiting; errors leave drafts intact. Grid measurement also records its calculated inputs as drafts. Artwork upload, Wi-Fi, visibility-mode and enable controls retain their existing immediate-save behavior. Drafts are not campaign persistence or cross-browser conflict resolution and do not survive reload.

At the Phase 1 checkpoint the server still used one active map for DM and players. The following campaign workspace extension implements the separately authorized TM-A through TM-F. TM-G physical connections remains deferred.


## Campaign workspace — 0.4.0

`campaigns.js` owns migration/validation and campaign/session/resource/identity/group commands, using the existing serialized mutation/store pipeline. No database, repository layer or second token/rendering engine was added. Persistent schema 2 has a versioned `workspace` containing campaigns (each with named sessions and their map references), reusable map defaults, token templates, persistent NPC identities and map groups. The top-level map records are continuing campaign-owned location instances. They retain materialized preparation snapshots for compatibility with the existing renderer; shared defaults are explicit snapshots for future instances, not aliases to live map progress.

`state.active` remains the player-published map, preserving phone/controller semantics. `workspace.selected` is the separately saved DM preparation map. `/api/state` adapts its `active` field to the DM selection and adds `published`; `/api/player` uses only the actual published map. Map mutations target the DM selection. `select` never publishes or blanks. `publish` selects the displayed map and explicitly shows it subject to the existing fog and panic-epoch checks. The first import may establish a covered/blank player map for compatibility; subsequent imports are private. A session switch can leave the current player map visible while preparing an empty/different session; no per-map operation can fall back to the player map when DM selection is null.

A new session copies references to current continuing locations, not state or definitions. A different campaign’s resource use creates independent progress. Explicit fresh-copy creation works within a campaign. Resource defaults contain image, dimensions, grid, geometry, compass and atmosphere only; they contain no fog, placements or credentials. New copies start covered with placement locked. Campaign switching clears publication, blanks the table, disables Wi-Fi and clears transient invitation/roll state. Controller lookup is limited to the current campaign; within it, phones still prepare profiles on inactive assigned maps and move only on the published map.

Named NPCs attach a campaign actor identity to the same token object. Moving removes the old placement and adds that token ID to a free square in the selected map, preserving its appearance and visibility. It is an explicit live move: if the source is published, its removal is visible immediately. Deleting the token removes that identity. Template snapshots contain only existing token defaults; spawning uses new server-generated IDs/keys and the existing occupancy logic. Groups reference resource IDs and floor navigation resolves prepared instances, without implied spatial links.

Before migrating an existing schema-1 file, Store preserves `session.before-campaign-workspace-v1.json` without overwriting an earlier snapshot. Reading upgrades in memory; a successful save commits schema 2 through the existing atomic replacement. Older binaries reject schema 2. Full exports retain all workspace metadata and image assets; restore continues to create a new directory. The 0.4.0 review installation/data/port are separate from accepted 0.3.0 for rollback.
